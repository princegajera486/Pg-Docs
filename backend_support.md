## MODULE 1: AUTHENTICATION

### 1. Module Overview
The Authentication module handles admin login, session management, and JWT generation for securing all subsequent API requests.

### 2. Firebase Database Structure
- **Node Name**: `admins`
- **Purpose**: Stores administrator credentials.
- **Child Nodes**: `{admin_id}`
- **Data Types**: String, Boolean
- **Required Fields**: `email`, `password_hash`, `is_active`
- **Optional Fields**: `last_login`
- **Firebase Key Structure**: Push ID generated by Firebase (`-N...`) or deterministic string.
- **Sample JSON**:
```json
{
  "admins": {
    "admin_1": {
      "email": "admin@pg.com",
      "password_hash": "$2b$12$e/...",
      "is_active": true,
      "last_login": "2023-10-01T10:00:00Z"
    }
  }
}
```

### 3. Firebase Relationships
- Standalone node. Admin IDs may be referenced in logs or audit nodes, but are functionally independent for authentication.

### 4. FastAPI Endpoints
| Method | Endpoint | Description | Authentication |
| :--- | :--- | :--- | :--- |
| POST | `/api/v1/auth/login` | Admin login | No |
| POST | `/api/v1/auth/refresh` | Refresh access token | Yes |
| GET | `/api/v1/auth/me` | Get current admin profile | Yes |
| PUT | `/api/v1/auth/me` | Update profile (Edit API) | Yes |

### 5. Request Payload
**POST `/api/v1/auth/login` (Create API)**
```json
{
  "email": "admin@pg.com",
  "password": "SecurePassword123!"
}
```
**PUT `/api/v1/auth/me` (Edit API)**
```json
{
  "email": "newadmin@pg.com"
}
```

### 6. Response Payload
**Success (200 OK)**
```json
{
  "access_token": "eyJhbGci...",
  "refresh_token": "eyJhbGci...",
  "token_type": "bearer"
}
```
**Error (401 Unauthorized)**
```json
{
  "detail": "Invalid credentials"
}
```

### 7. Backend Validation Rules
- **Required validation**: `email` and `password` are mandatory.
- **Business validation**: Check `is_active == true`.
- **Firebase validation**: Admin node lookup by email.
- **Duplicate validation**: N/A for single admin flow.

### 8. Business Logic
Receive Credentials -> Validate Email Format -> Query Firebase `admins` node by email -> Verify bcrypt password hash -> Check `is_active` -> Generate JWT Access Token -> Return Success.

## MODULE 2: PG MANAGEMENT

### 1. Module Overview
Manages the properties, rooms, and bed configurations across multiple PG locations based on the multi-step onboarding form.

### 2. Firebase Database Structure
- **Node Name**: `pg_properties`
- **Purpose**: Stores details of all PG buildings.
- **Child Nodes**: `{pg_id}`, `rooms`, `beds`
- **Data Types**: String, Integer, Boolean, Array
- **Required Fields**: 
  - **Basic Info**: `code`, `name`, `type`, `gender_type`, `contact_person`, `mobile`
  - **Address**: `address_line_1`, `area`, `city`, `state`, `pincode`, `country`
  - **Config**: `no_of_rooms`, `property_status`
- **Dynamic Room Fields** (Depends on `type`):
  - **If type == 'PG'**: `room_number`, `sharing`, `rent`
  - **If type == 'Apartment'**: `flat_no`, `bhk`, `rent`
- **Optional Fields**: 
  - **Basic Info**: `description`
  - **Address**: `address_line_2`, `landmark`
  - **Amenities**: `amenities` (List of strings)
- **Firebase Key Structure**: Firebase auto-generated Push IDs (e.g., `-Nabc123...`)
- **Sample JSON**:
```json
{
```

### 3. Firebase Relationships
- Nested structure: `pg_properties` -> `rooms` (acting as flats for Apartments) -> `beds` (only for PGs).
- Bed IDs are referenced by the `Members` node to indicate occupancy (for PG type).
- Room/Flat configuration is dynamically generated based on `no_of_rooms`. 
  - If `type == 'PG'`, `beds` are auto-generated based on the `sharing` value.
  - If `type == 'Apartment'`, `beds` are NOT generated, and it represents a flat (`flat_no`, `bhk`).
- Real-time updates: Changing a bed's `is_occupied` to `true` reflects immediately in Dashboard aggregations.

### 7. Backend Validation Rules
- **Required validation**: All fields marked required (e.g., `code`, `name`, `type`, `address_line_1`, `city`, `pincode`, `no_of_rooms`, `property_status`, etc.).
- **Dynamic Rooms Validation**: The number of items in the `rooms` array must exactly equal `no_of_rooms`. 
  - For `PG` type, `room_number`, `sharing`, and `rent` are required.
  - For `Apartment` type, `flat_no`, `bhk`, and `rent` are required.
- **Duplicate validation**: Ensure PG `code` and `name` don't already exist.
- **Business validation**: Cannot delete a PG if it has occupied beds or active flats.
- **Firebase validation**: Verify valid Firebase Key for PUT/PATCH/DELETE.

### 8. Business Logic
Receive Payload -> Validate fields -> Check Dynamic Rooms count against `no_of_rooms` -> Check Duplicate Code/Name -> Create PG node in `pg_properties` -> Iterate through `rooms` array -> Create room/flat nodes -> If `type == 'PG'`, auto-generate `beds` based on `sharing` -> Return Success.

## 9. Service Layer
The architecture uses Service Layer classes to separate business logic from routing.
- **AuthenticationService**: Handles JWT creation, payload decoding, and password hashing.
- **DashboardService**: Fetches and aggregates KPI data. Uses Firebase queries to count metrics.
- **PGService**: Manages the hierarchy of PGs, Rooms, and Beds.
- **MemberService**: Handles onboarding, profile updates, and triggering bed state changes.
- **PaymentService**: Handles manual verification logic, checking payment statuses, and updating rent records.
- **StatementService**: Uses PDF parsing libraries, implements matching algorithms, and updates records.
- **NotificationService**: Generates WhatsApp links and pushes notifications.
- **FirebaseService**: Centralized service wrapping the Firebase Admin SDK for DB and Storage interactions.

---

## 10. Firebase Operations
Firebase Realtime Database interactions:
- **Create**: Using `.push()` equivalent in Admin SDK to auto-generate unique keys.
- **Read**: Using `.get()` for single fetch, `.order_by_child()` for filtering (e.g., fetching active members).
- **Update**: Using `.update()` for modifying specific child nodes without overwriting.
- **Delete**: Using `.delete()` to remove nodes.
- **Batch Update**: Sending a dictionary of multiple paths to `.update()` on the root reference for atomic multi-location updates.
- **Transaction**: Using Firebase transaction blocks to handle concurrent bed allocations.
- **Real-time Listener**: Backend generally uses REST/Admin SDK fetching, but workers can use listeners for queue processing.
- **Atomic Update**: Utilizing path-based updates (`members/-N123/status: Inactive`).
- **Offline Synchronization**: Mostly relevant for frontend SDKs, backend uses Admin SDK which operates online.

## 11. Authentication
- **JWT Authentication**: Secure API endpoints via stateless JSON Web Tokens.
- **Login Flow**: Admin provides email/password -> Backend verifies against Firebase `admins` node -> Returns JWT.
- **Access Token**: Short-lived (e.g., 15 mins).
- **Refresh Token**: Long-lived (e.g., 7 days) to get new access tokens.
- **Password Hashing**: `bcrypt` ensures raw passwords are never stored.
- **Session Expiration**: Enforced by JWT expiration claim (`exp`).
- **Single Admin Login**: System designed for a single admin/owner structure.

## 12. Exception Handling
FastAPI Exception Handlers to return standardized JSON responses.
- **ValidationException** (422): Pydantic input validation failures.
- **FirebaseException** (500): Database connectivity or SDK errors.
- **AuthenticationException** (401): Invalid or expired JWT.
- **DuplicateException** (409): Resource already exists (e.g., Mobile number).
- **BusinessException** (400): Domain logic violations (e.g., Bed already occupied).
- **FileUploadException** (400): Invalid file format/size.
- **StatementProcessingException** (422): Failure to parse PDF or wrong password.
- **PaymentException** (400): Invalid payment transition state.
- **NetworkException** (503): Third-party API failures.

## 16. Payment Verification Flow
1. **Rent Due**: Background job creates `Pending` record in `rent_records`.
2. **WhatsApp Link Generated**: Notification service creates a secure JWT-based payment link.
3. **Member Opens Link**: Member sees UI with due amount.
4. **Select Payment Method**: Chooses UPI.
5. **UPI App Opens**: Member pays via intent link.
6. **Payment Completed**: Member uploads screenshot.
7. **Screenshot Uploaded**: Saved to Firebase Storage, URL attached to rent record.
8. **Status becomes "In Review"**: `rent_records` node updated.
9. **Admin Verification**: Admin reviews on dashboard.
10. **Approved -> "Paid"**: Record updated. OR **Rejected -> "Rejected"**: Record updated, member notified to retry.

## 17. Bank Statement Upload Flow
1. **Admin Uploads Bank Statement PDF**: API receives file.
2. **Validate PDF**: Check mime type.
3. **Validate Password**: Use password if provided for protected PDFs.
4. **Extract Transactions**: Use PyMuPDF/pdfplumber to read tabular text.
5. **Read Transaction Details**: Parse Date, Amount, Remarks/UPI ID.
6. **Match Transactions with Pending Member Payments**: Logic matches amount and fuzzy-matches remarks with tenant name or mapped UPI IDs.
7. **Update Matching Records**: Prepare Firebase Batch Update.
8. **Mark Payment Status**: Change matched rents to 'Paid'.
9. **Generate Processing Summary**: Store results in `statements` node (Success count, Unmatched count).

## 20. Security
- **JWT Security**: Signed with HS256, verified via FastAPI dependencies.
- **Password Hashing**: `bcrypt` ensures raw passwords are never stored.
- **Firebase Security Rules**: DB locked down (`".read": false, ".write": false`) since all interaction happens via backend Admin SDK.
- **Input Validation**: Pydantic strictly checks types and formats.
- **API Rate Limiting**: Limit `/login` and `/upload` endpoints to prevent brute force.
- **File Upload Security**: Validate extensions and magic bytes. Enforce size limits.
- **Secure File Access**: Pre-signed URLs expire after a set time.
- **HTTPS Enforcement**: Standard on production servers.
- **CORS Configuration**: Allowed origins restricted to the known frontend URL.
- **Request Validation**: Reject extra payload fields.
